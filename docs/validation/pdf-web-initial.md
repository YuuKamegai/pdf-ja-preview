### 並列実行で固まる問題（原因を特定して修正した）

検証中、`test:web` を通しで回すと稀に固まり、10 分以上返らないことがありました。
一度は 4 件が失敗し、`extractor.test.ts` だけで 472 秒かかっています。単独で回すと
90 ミリ秒で終わる試験だったので、当初は負荷による遅延と見ていました。**そうではなく、
再現する不具合でした。**

原因は打ち切り処理の多重起動です。stdout が上限（32 MiB）を超えても `'data'` は
届き続けるため、chunk のたびに後始末が呼ばれ、そのたびに `taskkill` を起動していました。
**1 回の実行で 274 回**（実測）。子が死ぬのが遅れるほど chunk が増えて起動も増える
悪循環になり、機械が飽和して無関係な試験まで巻き添えになります。飽和すると
`Get-CimInstance` のような軽い問い合わせすら 2 分で返らなくなりました。

打ち切りを一度だけにして直しました（`stop()` を冪等に）。`huge` の試験は 487 ミリ秒で
終わるようになり、`test:web` は 5 回連続で 14–15 秒・217 件成功。失敗した並びと
同じ順番（`npm test` → `typecheck:web` → `test:web` → …）でも再現しません。

`test_extractor` に後始末が 1 回しか走らないことを確かめる試験を足してあります。

なお、セッション開始時に**前のセッションが残した孤児プロセス**（`fixture-server.ts` と
`fake-worker --mode spin` 3 件）が動いており、これがある間も `test:web` が返りませんでした。
孤児を落としたら即座に完走しています。

## 3. 実 Docling（抽出）

### 3.0 合成 fixture と manifest

`test/fixtures/pdf/` の合成 PDF 7 件について、ページ寸法・回転・CropBox 原点・状態と、
段落ごとの期待矩形・読み順を `expected.json` に**人が独立に記録**しています。抽出器の
出力からは作っていません。値は生成スクリプトの描画位置と pypdfium2（抽出器とは別経路）が
返す行の矩形から求め、レンダリング画像を目で見て確かめました。

| fixture | 何を確かめるためのもの | 実 Docling の結果 |
|---|---|---|
| `two-column.pdf` | 二段組みの読み順（縦位置で並べると壊れる配置） | 期待どおり |
| `general.pdf` | 一段組みの一般文書、2 ページ | 期待どおり |
| `cropbox.pdf` | 非ゼロ CropBox（原点 10, 20） | 期待どおり |
| `rotated.pdf` | 0 / 90 / 180 / 270 度 | 90 度ページは横倒しの文字が図として検出される（既知の逸脱） |
| `image-only.pdf` | 文字の無い図だけのページ | `no-text` になる |
| `formula.pdf` | 行を分けて中央に置いた数式 | **`formula` として立たない**（下記 3.5） |
| `page-spanning.pdf` | 改ページをまたぐ段落 | **2 ページ分の領域を持つ 1 ブロックになる**（下記 3.5） |

`formula.pdf` と `page-spanning.pdf` はこの検証で追加したものです。それまで manifest に
数式とページまたぎの紙がなく、**「複数ページ出典」の扱いは単体試験だけで、実 PDF では
一度も確かめられていませんでした。**


### 3.1 最終テスト対象（実文書）

`<手元の実文書 PDF>`（Nature Aging 2024、
二段組み英語論文、5.33 MiB、sha256 `85803a21…8a5049`）。**リポジトリには入れていません。**

| 項目 | 値 |
|---|---|
| 抽出時間 | 23,379 ms |
| ページ数 | 26（`ok` 23 / `no-text` 3 / `failed` 0） |
| ブロック数 | 3,701 |
| 訳す対象 | 311（104,626 文字） |
| 種別内訳 | paragraph 3,469 / list 97 / furniture 67 / heading 38 / picture 15 / caption 15 |
| 警告 | ページ 24・25・26 からは文章を抽出できません / 図や表の中の文字 3,253 件は訳しません |

ページ 24–26 は補足の図版ページで、実際に文字が入っていません。`no-text` の判定は正しく、
「全ページが OCR 不足」と決めつけてはいません。

### 3.2 配布条件を確認した公開文書

| 文書 | 配布条件 | ページ | ブロック | 訳す対象 |
|---|---|---|---|---|
| arXiv 2609.19122（二段組み論文） | CC BY 4.0（abstract ページで確認） | 5 | — | 87 |
| PLOS ONE `10.1371/journal.pone.0173664` | CC BY 4.0（PLOS の Licenses and Copyright で確認） | 17 | 269 | 184 |
| NIST SP 800-63B（一般文書・一段組み） | 合衆国政府の著作物。米国内で著作権の対象外 | 80 | — | 761 |

**これらもリポジトリには入れていません。** 手元の作業ディレクトリへ落として抽出しただけです。

### 3.3 読み順（二段組み）

「右段の先頭が左段の続きより上にある」＝縦位置で並べると壊れるページについて、
本文ツリー由来の読み順が左段→右段になっているかを機械的に確認しました。

- **arXiv 2609.19122: 両段のある 5 ページすべてで左→右。壊れ 0。** 5 ページとも
  「縦位置なら壊れる罠」に該当します。
- PLOS ONE: 本文は一段組みで、二段になるのは Author Contributions と References のみ。
  目視で順序の崩れはありませんでした。
- Tsugawa（Nature Aging）: 1 ページ目は左に受理日・著者の袖、右上に DOI、中央に要旨、
  下に二段本文という構成で、袖と本文が混ざる順になりますが、**読む順としては正しい**
  ことを原文と突き合わせて確認しました。本文が二段で続く 9 ページ（p2, p9, p12–p18）は
  すべて左→右です。

### 3.4 抽出で崩れた箇所と、その対応

| 崩れ | 対応 |
|---|---|
| 図の枠が取れないページで、目盛り（`4.5`）・パネル記号（`a`）・記号（`*`, `+`）が訳す対象に入っていた。実文書で 366 件中 **55 件** | **修正した。** 英字が 2 つ続かないものは訳すものが無いので訳す対象から外す（`normalize.py`）。公開文書 3 件・訳す対象 1,032 件では 1 件も落ちないことを確認 |
| 上の修正で、同じ断片が「図へ畳む」処理を素通りし、図との対応（`relatedIds`）を失った | **修正した。**「訳さない」と「図に属する」を別の判断にした。畳んだ件数の警告も 3,253 件に戻った |
| 画面の進み具合が「訳済み 7 / **3701**」と出ていた（分母が全ブロック） | **修正した。** 分母を文書の訳す対象（311）にした。一時停止で待機に戻っても減らない |
| 所属の脚注が本文段落の先頭に連結される（p1 の `A full list of affiliations appears…`） | **未修正。** 既知の制約として記録 |
| 図の枠が取れない全面図のページで、55 件の断片が図へ畳まれず訳文側に素のまま並ぶ | **未修正。** 訳しはしないので LLM は呼ばないが、その列は読みにくい。初期版は図中の文字を対象外としているため、既知の制約として記録 |

### 3.5 実 PDF で確かめた設計上の前提

| 前提 | 結果 |
|---|---|
| 改ページをまたぐ段落は 1 ブロックにまとまり、領域を 2 つ持つ | **成り立つ。** `page-spanning.pdf` で、1 ページ目の途中で切れた文が 2 ページ目の続きと 1 つの `source` にまとまり、`regions` が `[1, 2]` になることを確認 |
| 数式は `formula` として立ち、訳さずに残せる | **成り立たない。** 文字で描いた数式（`dC/dt = D * d2C/dx2 + k * C`）は 1 行目が `paragraph`、2 行目が `heading` になった。`formula` は 1 件も立たない |

数式の件は、`docs/pdf-web.md` に既に書いてある「区切り記号の無い数式は自動では
見分けられない」の実例です。**直していません**が、現状を固定する試験
（`test_text_drawn_formula_is_not_recognised_as_a_formula`）を置いたので、
Docling 側が立てるようになったらその試験が落ちて気づけます。

## 4. 実 Ollama（翻訳）

モデルは起動中の Ollama にあった `qwen3.5:9b-q4_K_M` を使いました。**巨大モデルを
勝手に取得していません。**

対象は Tsugawa 論文の先頭 60 ブロック（`--max-blocks 60`）。文書全体（311 ブロック）は
訳していません。

| 項目 | 値 |
|---|---|
| 翻訳時間 | 160,691 ms（60 ブロック、並列度 1） |
| 成功 | 56 |
| 失敗 | 4 |
| 終了コード | 3（全件成功ではないので成功扱いにしない） |

### 4.1 失敗の内訳（すべて保護対象の検査が止めたもの）

| code | 内容 |
|---|---|
| `placeholder-missing` | 訳文から「1」が落ちています（著者の肩付き番号） |
| `placeholder-missing` | 訳文から「136」が落ちています |
| `placeholder-missing` | 訳文から「1」が落ちています（`Extended Data Fig. 1`） |
| `identifier-missing` | 識別子が訳文から落ちています: `AIN-93M`（2 番目のかたまり） |

**4 件とも、モデルが実際に数値・識別子を落としたものです。** 検査が誤検知したのでは
ありません。失敗したブロックは原文表示のまま残り、画面に理由と「訳し直す」が出ます。
数値・引用を黙って落とした訳が確定しないことを、実文書で確認できました。

### 4.2 数値・引用・数式の保持（目視）

本文の長い段落では、引用番号（`1`, `2-5`, `6-9`, `10`–`13`）、DOI、メールアドレス、
`2,704`・`109` のような数値、`Gal2Cer` / `Hex3Cer` / `UGT8A` のような識別子が
そのまま残っていることを原文と突き合わせて確認しました。訳文の質も、本文の散文に
ついては読める水準です。

### 4.3 目視で見つけた訳の崩れ（未修正・既知の制約）

| 崩れ | 例 |
|---|---|
| 短い日付の断片で月名が落ち、年月が入れ替わる | `Received: 30 October 2022` → `提出：30 年 2022 月` |
| 隣の見出しが訳文に紛れ込む | `https://doi.org/...` → `Resource https://doi.org/...` |
| 専門語の揺れ | MUFA を「一重不飽和脂肪酸」（正しくは一価不飽和脂肪酸） |

いずれも**数値・識別子の保護検査は通ってしまう**種類の崩れです（数字は残っているため）。
訳文の意味の正しさは保証の対象外であることを `docs/pdf-web.md` に明記しています。

### 4.4 キャッシュ

**上の 160,691 ms はキャッシュ無しの値です。** `scripts/validate-pdf.ts` は実行のたびに
使い捨ての保存領域（`mkdtemp`）を使うので、繰り返しても前回の訳を再利用しません。
測定としてはこれで揃いますが、キャッシュの確認には使えません。

キャッシュの確認は実サーバー（永続の保存先）で別に行いました。`general.pdf` を開いて
訳し終えたあと、同じ文書をもう一度開き直したときの様子です。

| 何 | 結果 |
|---|---|
| ディスク上の訳キャッシュ | `docs/<文書のsha256>/tr/` に 6 件 |
| 開き直して全 6 ブロックが `translated` になるまで | **287 ms** |
| 比較: LLM 1 回の呼び出し | 約 900 ms（1 回目は 6 ブロックで 4,421 ms） |

6 ブロック分を 287 ms で満たしているので、LLM を呼び直していません。
文書を切り替えて戻したときも同じ経路です。

## 5. 実ブラウザでの縦断確認

実サーバー（`node dist-web/server.cjs`、`127.0.0.1:7391`）に実文書を読み込ませ、Edge で
確認しました。

- PDF は抽出を待たずに即表示される。ページ送り・ページ数（`/ 26`）が出る。
- 抽出が終わると訳文が並び、`一部のみ抽出` と `訳済み 8 / 311（失敗 1）` が出る。
- 訳文を押すと原文の該当箇所が光る。
- 失敗したブロックは原文のまま、赤字の理由と「訳し直す」が出る。
- **外部への通信が 1 件も無いこと**を `page.on('request')` で確認（`blob:`/`data:` と
  自サーバー以外は 0 件）。
- 「閉じる」で表示が片づく。

### 5.1 異常終了からの回収

1. 文書を登録して開いたまま、サーバーを `Stop-Process -Force` で強制終了。
2. `%LOCALAPPDATA%\pdf-ja-preview\tmp\<サーバーID>\*.pdf` が 1 件残ることを確認。
3. サーバーを起動し直すと、残っていた PDF とディレクトリが**回収されて 0 件**になり、
   新しいサーバーのディレクトリだけが残ることを確認。

### 5.2 障害の再現（既存の Ollama は止めていません）

無効な設定を与えて、止まらずに理由が出ることを確認しました。

| 壊し方 | 結果 |
|---|---|
| `PDF_JA_EXTRACTOR_IMAGE=pdf-ja-no-such-image:0` | 文書が `error` になり `worker-failed`「抽出プロセスが結果を返しませんでした (exit 125)」 |
| `PDF_JA_OLLAMA_ENDPOINT=http://127.0.0.1:1`（何も待ち受けていない） | ブロックが `error` になり `translation-failed`「Ollama へ接続できません: http://127.0.0.1:1」 |

どちらも固まらず、理由の分かる形で失敗します。
